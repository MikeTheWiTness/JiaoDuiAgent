# ADR 0010：Harness / ReAct / Plan Mode 升级 —— 基于 Claude Code 架构参考

**状态**：提议中
**日期**：2026-06-30
**决策者**：MikeTheWiTness
**相关 ADR**：[[ADR 0005 ReAct 机制核心架构]](0005-react-mechanism-architecture.md)、[[ADR 0006 物理 ReAct 学科化]](0006-physics-react-subject-specialization.md)
**参考源码**：Claude Code v2.1.88（`src/query.ts`, `src/Tool.ts`, `src/tools/EnterPlanModeTool/`, `src/tools/ExitPlanModeTool/`）

---

## 背景

当前 ReAct 校对流程存在两个结构性问题：

1. **工具结果无塑形**：LLM 发起的每个工具调用，原始结果直接塞回 messages。LLM 拿到结果后"迷路"——不知道下一步该做什么、处于什么阶段、该输出什么格式。结果：格式不准确、校对结果丢失。

2. **格式防线单薄**：仅靠 system prompt 中的格式要求（第一层）+ `format_enforcement.py` 事后修正（第四层），缺少中间层。一旦 LLM 在循环中走偏，只能等全部结束后再救火。

对 Claude Code 源码的分析揭示了三个可借鉴的模式：
- **`mapToolResultToToolResultBlockParam`**：工具结果不只是数据返回，而是"状态指令注入点"
- **Plan Mode = 工具 + 状态机**：用工具调用切换权限模式，无需独立 agent
- **后置闸门**：LLM 自然停止后系统静默检查，不打扰 LLM 的正常工作流程

---

## 决策

### A. 工具结果塑形（`shape_result`）

每个工具新增 `shape_result(raw_output) -> str` 方法，负责：

1. **截断**：限制结果大小（默认 6000 字符），防止撑爆上下文
2. **结构化标记**：给结果加清晰的边界，让 LLM 识别"这是工具返回"
3. **上下文提示**：根据工具类型给出简短引导，如"以上是原文内容，请仔细比对"

```python
class WebSearchTool(BaseTool):
    def shape_result(self, raw_output) -> str:
        base = default_shape_result(str(raw_output))
        return f"[搜索到约 N 条结果]\n\n{base}"
```

- 每个工具独立实现 `shape_result()`，不使用 Mixin 或继承
- 工具不感知全局状态（不处理阶段切换逻辑）
- 默认截断函数作为公共工具函数提供

### B. 阶段切换：自然结束 + 后置格式闸门

**不做 plan_update 拦截**。Claude Code 的模式是：LLM 自己决定何时停止调用工具（`stop_reason = end_turn`），系统在循环退出后做后置处理。

当前 `call_api` 的 `while finish_reason == "tool_calls"` 已经是这个模式。升级方案：

```
LLM 在 ReAct 循环中自由使用 plan_update 管理自己
  ↓
LLM 自然结束（不再调工具）→ 循环退出
  ↓
Python 端拿到最终输出 → 静默检查格式（LLM 不知道）
  ↓
  ├─ 通过 → 返回结果
  └─ 失败 → 注入修正指令 + 继续循环（仅 bash/read_file/write_file）
            → 再次检查 → 最多 3 轮 → 还失败就标记
```

- plan_update 完全不动，nudge 行为保持现状
- `pre_hook`（预处理：文言文/诗歌前置搜索）保持独立，不纳入阶段管理
- 阶段切换不需要 LLM 主动调用新工具

### C. 多层格式防线（简化为三层）

| 层 | 位置 | LLM 是否感知 | 说明 |
|---|------|-------------|------|
| 第 1 层 | system prompt 中的格式要求 | 是 | 一次性，已有 |
| 第 2 层 | 输出阶段静默闸门 | 否 | 新增——Python 端检查，失败时才注入指令 |
| 第 3 层 | 格式重试兜底 | 是 | 新增——3 轮重试后标记 `⚠️ 格式不合规` |

取消原先设想的"工具塑形中夹带格式提醒"（第 2.5 层），保持闸门静默。

### D. 格式重试机制

**位置**：`call_api` 内部扩展循环（不等外部 `enforce_and_fix`）。

**重试时工具限制**：仅保留 `bash`、`read_file`、`write_file`（硬编码名单），关闭所有分析工具（web_search、locate_paragraph、read_section、sympy 系列）。

**重试指令渐进升级**：

| 轮次 | 指令风格 | 示例 |
|------|---------|------|
| 第 1 轮 | 简短指令 | "格式检查未通过。请用 read_file 读取上一轮输出，修正后用 write_file 写回。" |
| 第 2 轮 | 带格式模板 | "格式仍未通过。请严格遵守 ### 标记原文 + ### 修改原因 格式重新输出……" |
| 第 3 轮 | 警告威胁 | "已两次格式不通过。这是最后一次机会，否则将标记为格式不合规。" |

**外部兜底移除**：不再另起 LLM 会话做格式修正。3 轮失败后直接标记，保留中间产物供人工排查。

### E. 中间产物保留

以下中间产物全程落盘，不只在最终成功时保存：

1. 每个工具调用后的 `shape_result()` 输出
2. 格式检查不通过时的注入指令文本
3. 每次重试的原始输出和修正后输出
4. 完整 API 对话记录

### F. 结果标记

- **无错误**：输出前追加 `✅ 校对完成，未发现错误`
- **格式失败**：3 轮重试仍不通过 → 输出前追加 `⚠️ 校对格式不合规，请查看中间文件`

## 不纳入

| 项目 | 原因 |
|------|------|
| 流式工具执行 | 侵入性大，不影响格式准确性，后续单独评估 |
| 并发工具执行 | 同上 |
| 工具类别标记（`phase` 属性） | 用硬编码名单替代，足够简单 |
| 学科 subject.py 基类提取 | 6 科重复度极高，但单开重构（见 ADR-0011） |
| 图片复制逻辑统一 | 同上 |
| config.json 格式规则去重 | 同上 |

## 后果

### 正面

- **格式合规率预期显著提升**：多层防线 + 工具塑形引导，LLM 每一步都收到清晰的状态指引
- **减少格式丢失**：静默闸门不过不放过，3 轮重试兜底
- **排查可追溯**：全程中间产物落盘，任意一步出问题都能回溯
- **架构更干净**：去掉外部 `enforce_and_fix` 的独立 LLM 调用，一个会话搞定全流程

### 风险

- `call_api` 内部循环扩展 → 函数复杂度增加，需要充分测试
- `shape_result` 逐个实现 → 初期工作量大（~16 个工具），但后续新增工具时模式已建立
- 格式重试依赖 LLM 的 bash 能力 → 若 LLM 在重试中滥用 bash 做其他事，需要日志监控
- 硬编码工具名单 → 新增工具时需手动更新 `OUTPUT_STAGE_TOOLS`
