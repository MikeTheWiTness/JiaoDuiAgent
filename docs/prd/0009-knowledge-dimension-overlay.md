# PRD：高中语文知识类校对维度叠加架构

**关联 ADR**：[0009-chinese-knowledge-dimension-overlay](../docs/adr/0009-chinese-knowledge-dimension-overlay.md)
**状态**：待实现
**日期**：2026-06-30

---

## 问题陈述

用户目前可以向校对工具发送 Word 文档进行校对，但工具对"知识类讲义"（写作素材讲义、字音字形表、病句归纳、修辞体系讲解等）的校对能力严重不足：

1. **没有知识类 ReAct 校对流程**。现有 `knowledge_prompt_lines` 是扁平 prompt（ADR-0005 之前的旧模式），不支持工具调用、不享受 plan_update 进度标记、不做格式自检
2. **切割方式不适配**。知识讲义不是按题目分块——一个素材条目是 2K-10K 字符的自封闭单元，现有 `smart_split` 的"全文+标签输出"模式在长文档下容易输出截断
3. **用户需要手动选择模式**。"题目"和"知识"各走各的 prompt，用户必须在 UI 中明确区分
4. **校对重点因内容而异**。写作素材讲义需要检查"引喻失义/强行贴标签"，字音字形表需要检查"拼音标注准确性"——一个固定 todolist 无法覆盖

## 解决方案

**统一入口 + 维度叠加架构**：用户发送任意 Word 文档 → 工具自动切割 → LLM 第 0 步判断"题目/知识"→ 题目走 ADR-0008 节点图，知识走维度叠加组装 todolist。

## 用户故事

1. 作为一名语文教研员，我希望将写作素材讲义扔进校对工具后，工具能自动识别素材条目中的"引喻失义"问题，而不是只扫错别字
2. 作为一名语文教研员，我希望发送任意类型的语文文档（试卷/讲义/知识表）时，不需要在 UI 中手动切换"题目模式"或"知识模式"
3. 作为一名语文教研员，我希望知识讲义中嵌入的例题能自动被识别并按题目流程校对
4. 作为一名语文教研员，我希望知识讲义的古文引用不会被误标为"错别字"（通假字为正常现象）
5. 作为一名语文教研员，我希望讲义的编号/层级/序号在校对时被自动检查连续性
6. 作为一名语文教研员，我希望校对报告中的出处引用在无法验证时被标记为"人工复核"，而不是 LLM 编造一个结论
7. 作为一名语文教研员，我希望我可以用人工标记（`###### 知识开始/结束 ######`）精确控制切割粒度
8. 作为一名语文教研员，我希望智能切割失败时工具自动降级为单单元校对，不阻塞工作流
9. 作为一名运维者，我希望新的知识校对流程在 token 消耗上不显著高于现有题目校对流程

## 实现决策

### 模块 1：统一 agent_prompt

**职责**：合并 ADR-0008 题目节点图与知识维度叠加到一个 prompt，第 0 步路由

**接口**：
- `config.json`：新增 `unified_agent_prompt_lines` 字段，保留旧 `agent_prompt_lines` + `knowledge_prompt_lines` 作 fallback
- `subject.py::get_question_prompt()` 和 `get_knowledge_prompt()`：ReAct 模式下统一返回 unified prompt；非 ReAct 模式下保持现有行为
- `subject.py::get_review_prompt()`：同上

**关键设计**：
- 第 0 步判据："题目"的特征是含题干引导语/选项/答案结构；"知识讲义"的特征是含素材条目/概念定义/方法步骤
- 知识维度触发条件用明确关键词（如"古文引用 = 含《》书名号+文言句式"），不用抽象描述
- 维度 todolist 组装后调用 plan_update 声明，步数与 ADR-0008 分支深度相当（5-8 步）

### 模块 2：知识切割管线

**职责**：将知识讲义切分为独立的校对单元

**新增文件**：`shared/knowledge_split.py`

**管线流程**：
```
步骤 1（Python）：结构扫描 → 提取目录树 + 行号区间 → 置信度分层（HIGH/LOW/NONE）
步骤 2（LLM，仅 LOW + NONE）：块分类 + 子边界识别 → 输出类型标注 + 边界
步骤 3（Python）：合并步骤 1 + 步骤 2 结果 → 生成锚点列表 → 校验（唯一性/重叠/覆盖）
步骤 4（bash）：逆序插入标签 → Python 复核（配对/空单元）
```

**置信度判据**：
- HIGH：块边界落在 `（N）` / `####` / `###` 等明确标题上，且块大小 ≤ 8000 字符
- LOW：块大小 > 8000 字符，或同级标题间无子标记
- NONE：500+ 字符内无任何结构信号

**降级策略**：步骤 2 LLM 失败 → 降级为单单元（整文档作为一个校对单元）

### 模块 3：知识手工标记

**职责**：支持人工标记切割边界

**修改文件**：`core/manual_split.py`

**标记格式**：
```
###### 知识开始 ######
（知识内容）
###### 知识结束 ######
```

**新增函数**：`split_by_knowledge_markers(md_content)` — 与现有 `split_by_manual_markers()` 同构，仅标记关键词不同

### 模块 4：类型路由（嵌入题目支持）

**职责**：切割阶段标记的 `<problem-strip>` 块走 ADR-0008 题目流程

**实现**：
- 切割标记输出中包含类型字段（`knowledge` / `problem-strip`）
- `subject.py` 中根据类型选择校对 prompt 路由
- 嵌套场景（知识块内嵌 `<problem>` 标记的题目）在切割时不拆，校对时由维度⑥触发走 ADR-0008

### 模块 5：UI 分割模式扩展

**职责**：split_mode combobox 新增知识类选项

**修改文件**：`ui/default_app.py`

**新增选项**：
- `knowledge_smart` — 知识（智能分割）
- `knowledge_manual` — 知识（人工标记）

**联动**：选中"知识"系列时，`source_mode` 联动为"讲义"；其余不变

### 模块 6：测试

**修改/新增文件**：`tests/test_knowledge_split.py`、`tests/test_split_modes.py`（扩展）

**测试策略**：
- 所有涉及 LLM 返回值的内容用 mock（`unittest.mock`），不发起真实 API 调用
- mock 返回固定锚点列表 / 固定类型标注，验证 Python/bash 管线行为
- 真实样本回归测试：用固定讲义文件走完整管线（含真实 LLM 调用），输出校对报告给人工评审

## 测试决策

### 什么构成好测试
- 只测试外部行为（切割结果的配对性、空单元检测、降级触发），不测试内部实现细节
- mock LLM 返回值的测试：验证管线对"正常 LLM 返回""异常 LLM 返回""LLM 返回格式错误"三种情况的处理
- 信心测试（smoke test）：真实讲义文件 + 真实 LLM 调用，人工评审校对报告质量

### 需要测试的模块

| 模块 | 测试类型 | 测试内容 |
|---|---|---|
| `knowledge_split.py` 步骤 1 | 单元（纯 Python，无 mock） | 置信度分层正确性；各种边界格式（编号/标题/无标记） |
| `knowledge_split.py` 步骤 3+4 | 单元 + mock | mock 步骤 2 的 LLM 返回 → 验证合并/锚点校验/bash 插入/复核 |
| `manual_split.py` 知识标记 | 单元（无 mock） | 配对检测、未闭合报错、嵌套兼容性 |
| `subject.py` 路由 | 单元 + mock | mock config → 验证 prompt 选择逻辑（ReAct/非ReAct、题目/知识） |
| 端到端 | 集成测试 | 两份讲义样本（格式规整 + 格式混乱），真实 LLM 调用，人工评审 |

### 测试先例
- `tests/test_split_modes.py` 已有 `TestManualMarker` 类和 mock LLM 模式（`test_split_mode_smart_with_mock`），知识标记和知识切割管线可以复用相同的测试结构

## 不纳入范围

- 新增知识专用工具（纯 prompt 层改动）
- 出处引用的外部知识库验证
- 切割步骤的 LLM 仲裁（复用现有两阶段确认）
- 其他学科的知识校对（待语文验证后推广）
- 物理/化学/数学等学科的独立解题增强

## 进一步说明

- 本 PRD 是 ADR-0009 的落地文档，所有技术决策以 ADR-0009 为准
- 改动面集中在 prompt 层 + 切割管线 + UI 选项，核心 API 调用和格式审查逻辑不变
- 旧的 `knowledge_prompt_lines` 保留作 fallback，不影响现有非 ReAct 用户
